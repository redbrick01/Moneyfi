# Transaction Ledger Redesign

This document defines the target transaction model before schema and code
migration. The goal is to make portfolio performance, realized profit,
cash-flow exclusion, income, fees, taxes, and FX flows derivable from a single
normalized ledger.

## Current Problem

The current local schema separates investment transactions from cash
transactions:

- `transactions`: investment-facing rows such as buy, sell, dividend, interest.
- `cash_transactions`: cash-account rows such as deposit, withdrawal, transfer,
  exchange, and trade settlement.

This works for basic display, but business meaning is still mostly encoded in
the Korean `type` text. Calculations must repeatedly infer whether a row changes
holding quantity, cash balance, realized profit, or performance cash flow.

## Target Principle

Use two layers:

- `transaction_events`: one user-visible event.
- `transaction_lines`: normalized accounting lines generated by the event.

An event describes what the user did. Lines describe what actually changed.
The event is for editing, grouping, sync, and display. Lines are the source of
truth for calculation.

## Event Kinds

`transaction_events.kind` is the broad category of a user action.

| Kind | Meaning |
| --- | --- |
| `opening_balance` | Initial balance or initial holding position. |
| `trade` | Buy or sell of an investment holding. |
| `cash_flow` | External cash deposit or withdrawal. |
| `cash_transfer` | Movement between cash accounts in the same portfolio. |
| `fx_exchange` | Currency conversion between cash accounts. |
| `income` | Dividend, interest, distribution, or reward income. |
| `fee` | Standalone fee not attached to another event. |
| `tax` | Standalone tax not attached to another event. |
| `adjustment` | Manual correction, split, merge, or reconciliation. |

## Line Actions

`transaction_lines.action` is the normalized calculation action.

| Action | Quantity Delta | Cash Delta | Performance Treatment |
| --- | ---: | ---: | --- |
| `opening_quantity` | yes | no | cost basis seed |
| `opening_cash` | no | yes | external capital |
| `buy` | positive | no | increases cost basis |
| `sell` | negative | no | creates realized PnL |
| `settlement` | no | yes | cash leg of trade |
| `deposit` | no | positive | external capital, excluded from pure return |
| `withdrawal` | no | negative | external capital, excluded from pure return |
| `transfer_out` | no | negative | internal movement |
| `transfer_in` | no | positive | internal movement |
| `fx_out` | no | negative | internal movement, FX source leg |
| `fx_in` | no | positive | internal movement, FX target leg |
| `dividend` | no | positive | investment income |
| `interest` | no | positive | investment income |
| `fee` | no | negative | performance cost |
| `tax` | no | negative | performance cost |
| `realized_pnl` | no | no | realized profit component |
| `adjustment` | optional | optional | explicit correction |

## Required Line Fields

Each line should be numeric and calculation-ready.

| Field | Purpose |
| --- | --- |
| `event_id` | Groups all lines that belong to one user action. |
| `action` | Normalized calculation action. |
| `asset_id` | Optional asset bucket. |
| `holding_id` | Present when the line changes an investment holding. |
| `cash_account_id` | Present when the line changes cash. |
| `currency_code` | Currency of the line amount. |
| `quantity_delta` | Signed holding quantity change. |
| `cash_delta` | Signed cash balance change. |
| `unit_price` | Trade unit price in source currency. |
| `gross_amount` | Absolute before-fee/tax amount. |
| `fee_amount` | Fee amount attached to this line or event. |
| `tax_amount` | Tax amount attached to this line or event. |
| `cost_basis_delta` | Signed cost basis change. |
| `realized_pnl` | Realized profit/loss produced by a sell. |
| `fx_rate` | Rate used for FX conversion. |
| `sort_order` | Stable ordering within an event. |

## Event Examples

### Buy

User action: buy 5 shares at 100 KRW.

```text
event.kind = trade
event.title = Buy TEST

line 1: action = buy
        holding_id = TEST
        quantity_delta = +5
        unit_price = 100
        gross_amount = 500
        cost_basis_delta = +500

line 2: action = settlement
        cash_account_id = KRW cash
        cash_delta = -500
```

### Sell

User action: sell 2 shares at 120 KRW. Average cost is 100 KRW.

```text
event.kind = trade
event.title = Sell TEST

line 1: action = sell
        holding_id = TEST
        quantity_delta = -2
        unit_price = 120
        gross_amount = 240
        cost_basis_delta = -200
        realized_pnl = +40

line 2: action = settlement
        cash_account_id = KRW cash
        cash_delta = +240

line 3: action = realized_pnl
        realized_pnl = +40
```

The separate `realized_pnl` line is optional if the sell line already carries
`realized_pnl`. If added, reporting should count exactly one source.

### External Deposit

User action: add 1,000 KRW to a cash account.

```text
event.kind = cash_flow
event.title = Deposit

line 1: action = deposit
        cash_account_id = KRW cash
        cash_delta = +1000
```

This increases assets but is excluded from pure investment return.

### Cash Transfer

User action: move 250 KRW from one cash account to another.

```text
event.kind = cash_transfer
event.title = Transfer

line 1: action = transfer_out
        cash_account_id = source cash
        cash_delta = -250

line 2: action = transfer_in
        cash_account_id = target cash
        cash_delta = +250
```

Both lines are internal movements and should not affect performance.

### FX Exchange

User action: exchange 130,000 KRW to 100 USD at 1,300.

```text
event.kind = fx_exchange
event.title = KRW to USD

line 1: action = fx_out
        cash_account_id = KRW cash
        currency_code = KRW
        cash_delta = -130000
        fx_rate = 1300

line 2: action = fx_in
        cash_account_id = USD cash
        currency_code = USD
        cash_delta = +100
        fx_rate = 1300
```

FX exchange is an internal movement unless a later feature explicitly realizes
FX gain/loss.

### Dividend

User action: receive 30 KRW dividend.

```text
event.kind = income
event.title = Dividend

line 1: action = dividend
        holding_id = source holding
        cash_account_id = KRW cash
        cash_delta = +30
        gross_amount = 30
```

Dividend is investment income and belongs in pure profit.

## Calculation Rules

- Holding quantity is `sum(quantity_delta)` for lines with `holding_id`.
- Cash balance is base balance plus `sum(cash_delta)` for lines with
  `cash_account_id`.
- Realized PnL is `sum(realized_pnl)` from sell or realized PnL lines.
- Dividend and interest income is `sum(cash_delta)` for `dividend` and
  `interest` lines.
- Fees and taxes reduce performance when their action is `fee` or `tax`.
- External deposits and withdrawals change capital but are excluded from pure
  investment return.
- Transfers and FX exchanges are internal cash movements and do not change
  performance by themselves.
- UI labels may be localized, but stored `kind` and `action` values should stay
  stable English enum strings.

## Migration Direction

Phase 2 should add the new tables alongside the existing tables. Existing
screens should keep using the old tables until conversion and parity tests are
ready.

Phase 2 status: local Drift tables and Supabase migration tables have been
added. They are intentionally not used by existing reads or writes yet.

Phase 3 should convert existing `transactions` and `cash_transactions` into
events and lines. The first validation target is parity:

- current holding quantity equals line-derived holding quantity.
- current cash balance equals line-derived cash balance.
- current average price equals line-derived moving-average cost basis.

Phase 3 status: a local legacy-to-ledger rebuild path, Supabase backfill
migration, and local parity validator have been added. The validator compares
legacy holding quantity and cash account balance against ledger-derived values,
so conversion drift can be caught in tests before more reads move over.

Phase 4 status: read-side performance and analysis calculations now use
`transaction_lines`/`transaction_events` through ledger APIs. Investment
performance, portfolio-level ledger summaries, dividend/interest analysis, and
transaction-date discovery no longer need to re-parse localized legacy
transaction categories for calculation. Legacy transaction rows are still used
for edit/detail display until write paths move over.

Phase 5 status: legacy transaction write paths now refresh the derived ledger
immediately after successful create, update, or delete operations. The app still
writes legacy tables first, but ledger reads no longer need to rebuild on every
aggregation call.

Phase 5 update: ledger refreshes from write paths now mark replacement
`transaction_events` and `transaction_lines` as dirty sync records. Replaced
ledger events are soft-deleted instead of physically removed, so remote sync can
receive both the deletion of the old ledger event and creation of the new one.
Legacy tables are still mirrored for edit/detail compatibility.

Phase 5 update 2: create paths now write ledger events and lines directly for
new standalone cash transactions and investment transactions. Legacy rows are
still inserted first for compatibility, but new ledger records are no longer
created by re-projecting the whole affected scope unless a parity fallback is
needed.

Phase 5 update 3: cash transfer and FX exchange create paths now write one
paired ledger event directly with source and target cash lines. They no longer
re-project the full cash ledger on create.

Phase 5 update 4: cash transaction update and delete paths now replace or
soft-delete only the affected ledger event. Investment update/delete still use
scoped re-projection because changing an earlier buy or sell can affect later
moving-average realized PnL.

Phase 5 update 5: investment update/delete scoped re-projection is now covered
by active/deleted ledger event tests. This keeps moving-average realized PnL
correct while still producing syncable soft-deleted ledger events for replaced
or removed transactions.

Phase 5 update 6: standalone cash-flow create now writes the ledger event and
line first, then creates the legacy `cash_transactions` mirror row and links the
event back to it. This is the first ledger-first write path.

Phase 5 update 7: cash transfer create now follows the same ledger-first
pattern: one `cash_transfer` event and two transfer lines are written first,
then the paired legacy `cash_transactions` mirror rows are created and linked
back to the event.

Phase 5 update 8: FX exchange and investment transaction create paths now also
write ledger events and lines first, then create legacy mirror rows and link
the events back to those rows. All create paths now have ledger-first coverage.

Phase 6 status: legacy writes now refresh scoped ledger projections instead of
rebuilding the full ledger. Investment mutations re-project the affected
holding's transaction chain so moving-average realized PnL stays correct; cash
mutations refresh the standalone cash ledger projection.

Phase 6 update: snapshot detail transaction lists now read from
`transaction_events` and `transaction_lines` instead of directly reading
`transactions` and `cash_transactions`. This removes another display-side
dependency on legacy transaction dates and localized legacy transaction rows.

Phase 6 update 2: holding detail investment transaction lists now read from
ledger holding lines. Trade rows derive their display amount from the
investment line and their cash-flow amount from the paired settlement line, so
detail screens no longer depend on legacy `transactions` rows for investment
history display.

Phase 6 update 3: `transaction_lines` now stores optional
`legacy_source_table` and `legacy_source_id` so each display/edit line can keep
its own compatibility pointer while reads move to the ledger. Cash detail
transaction lists now read from ledger cash lines instead of
`cash_transactions`, including transfer, FX, settlement, income, fee, tax, and
adjustment lines.

Phase 6 completion: user-facing transaction reads now come from the normalized
ledger for calculations, analysis, transaction-date discovery, snapshot detail,
holding detail, and cash detail. The old `transactions` and
`cash_transactions` tables remain as compatibility mirrors for current
edit/delete APIs, scoped re-projection, sync fallback, and older remote
payloads. They are no longer the primary display/calculation source.

Phase 7 status: normalized ledger tables are now included in local sync.
Dirty `transaction_events` and `transaction_lines` are uploaded with client-id
references, Supabase Edge Functions persist and return them, and local sync
restore uses remote ledger rows when present. If a remote payload does not yet
include ledger rows, the app rebuilds the ledger from legacy transaction tables.

Phase 8 status: portfolio-level performance aggregation now has a ledger API.
It separates realized PnL, income, fees, taxes, external cash flow, trade
settlement cash flow, and internal cash movement from `transaction_lines`.
Future performance screens can use this instead of re-parsing localized legacy
transaction categories.

Phase 9 status: portfolio-level ledger aggregation is available by currency,
and the investment performance screen now uses that currency-aware ledger
summary for realized PnL, income, buy amount, and sell amount totals. This keeps
KRW and USD ledger lines separate until the UI explicitly converts them.

Phase 10 status: investment performance now treats the ledger as the source for
expanded profit composition. Pure performance is calculated as realized PnL +
unrealized PnL + dividend/interest - fees - taxes, and the screen separately
shows excluded cash flows: external deposits/withdrawals, trade settlement cash
flow, and internal movement from transfers/FX. Tests cover fee/tax subtraction
from pure realized performance.

Phase 10 update: monthly realized performance is now derived directly from
`transaction_events.occurred_at` and `transaction_lines`. The ledger API groups
realized PnL, dividend/interest, fees, taxes, buys, and sells by month and
currency, and the investment performance screen shows recent monthly pure
realized performance after KRW conversion.

Phase 10 completion: investment performance now includes closed investment
positions when they have ledger activity, so fully sold holdings still
contribute realized PnL. The screen also includes a stock-level realized PnL
ranking based on ledger-derived holding performance. This completes the initial
profit/performance expansion pass: composition, excluded cash flows, monthly
trend, and per-holding realized ranking are all sourced from the normalized
ledger.

Only after parity is proven should reads and writes move to the new ledger.
