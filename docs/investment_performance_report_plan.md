# Investment Performance Report Plan

이 문서는 MONEYFY의 `투자성과 분석` 기능을 MVP 수준에서 제품급 성과 리포트로 확장하기 위한 개발 계획서입니다.

## Product Goal

사용자가 총자산 변화의 원인을 투자성과와 현금흐름으로 분리해서 이해하도록 돕습니다.

핵심 질문은 다음 세 가지입니다.

1. 실제 투자로 얼마를 벌거나 잃었는가?
2. 총자산 변화 중 입금, 출금, 이체, 환전 때문에 생긴 부분은 얼마인가?
3. 어떤 종목, 월, 수익원, 비용 항목이 성과에 가장 크게 기여했는가?

현재 앱에는 `transaction_events`와 `transaction_lines` 기반 원장 모델, `InvestmentPerformancePage`, 월별/종목별 ledger aggregate API가 이미 존재합니다. 따라서 이 계획의 방향은 신규 기능을 처음부터 만드는 것이 아니라, 기존 MVP를 더 정확하고 탐색 가능한 리포트로 확장하는 것입니다.

## Current Baseline

현재 구현된 기반은 다음과 같습니다.

| 영역 | 현재 상태 |
| --- | --- |
| 진입점 | 분석 탭의 `투자성과 분석` 카드 |
| 화면 | `lib/pages/investment_performance_page.dart` |
| 전체 집계 | `fetchLedgerPortfolioPerformanceByCurrency()` |
| 월별 집계 | `fetchLedgerMonthlyPerformanceByCurrency()` |
| 종목별 집계 | `fetchLedgerHoldingPerformanceByHoldingId()` |
| 성과 정의 | `실현손익 + 미실현손익 + 배당/이자 - 수수료 - 세금` |
| 제외 현금흐름 | 외부 입출금, 매매 결제 현금흐름, 내부 이동을 별도 표시 |
| 통화 처리 | 통화별 ledger 집계 후 화면에서 KRW 환산 |

현재 화면은 요약, 성과 구성, 제외 현금흐름, 월별 성과, 실현손익 랭킹, 보유 항목별 성과를 보여줍니다. 다음 단계에서는 기간 필터, 수익률, 기여도, 상세 drill-down, 검증 가능한 계산 규칙을 추가해야 합니다.

## Success Criteria

1차 제품화 기준은 다음과 같습니다.

| 기준 | 목표 |
| --- | --- |
| 이해 가능성 | 사용자가 총자산 변화와 투자성과의 차이를 한 화면에서 구분할 수 있음 |
| 정확성 | 입금/출금/이체/환전은 순 투자성과에 섞이지 않음 |
| 추적 가능성 | 월별, 종목별, 수익원별로 성과 원인을 확인할 수 있음 |
| 기간 탐색 | 1개월, 3개월, 6개월, 올해, 전체, 직접 선택을 지원 |
| 검증 가능성 | 주요 집계식이 unit/widget test로 고정됨 |

## Metric Definitions

성과 리포트의 표시 지표는 아래 정의를 기준으로 합니다.

| 지표 | 계산식 | 포함 항목 | 제외 항목 |
| --- | --- | --- | --- |
| 순 실현성과 | `실현손익 + 배당/이자 - 수수료 - 세금` | 매도 확정 손익, 배당, 이자, 수수료, 세금 | 미실현손익, 입출금, 이체, 환전 |
| 순 투자성과 | `순 실현성과 + 미실현손익` | 보유 중 평가손익까지 포함 | 입출금, 이체, 환전 |
| 미실현손익 | 현재 보유 평가금액 - 남은 원가 | 표시 대상 보유 종목 | 현금 평가 차이 |
| 외부 현금흐름 | `deposit + withdrawal + opening_cash` | 사용자 입금/출금/초기 현금 | 투자성과 |
| 내부 이동 | `transfer_out/in + fx_out/in`의 절대 이동량 | 계좌 이체, 환전 이동 규모 | 투자성과 |
| 결제 현금흐름 | `settlement` | 매수/매도 결제 현금 | 순 투자성과 산식에는 직접 미포함 |
| 총 성과 기여도 | 항목 성과 / 전체 순 투자성과 | 종목, 월, 수익원 | 전체가 0이면 표시 생략 |

주의할 점은 `settlement` 현금흐름은 사용자에게 거래 규모를 설명하기 위해 보여주지만, 순 투자성과 계산에는 직접 더하지 않는다는 점입니다. 성과는 `buy`, `sell`, `realized_pnl`, `dividend`, `interest`, `fee`, `tax`, 현재 평가손익에서 계산합니다.

## Proposed UX

### 1. Summary Header

상단은 기간 선택과 핵심 성과를 한 번에 보여줍니다.

| 요소 | 내용 |
| --- | --- |
| 기간 선택 | 1개월, 3개월, 6개월, 올해, 전체, 직접 선택 |
| 대표 지표 | 순 투자성과 |
| 보조 지표 | 순 실현성과, 미실현손익, 배당/이자, 비용 |
| 비교 문구 | "입출금 제외 기준"을 작은 설명으로 표시 |

예시:

```text
순 투자성과
+1,240,000원

실현 +420,000원 · 미실현 +690,000원 · 배당/이자 +160,000원 · 비용 -30,000원
입출금과 내부 이동은 제외한 성과입니다.
```

### 2. Waterfall Breakdown

총성과를 구성 요소별로 분해합니다.

| 순서 | 항목 |
| --- | --- |
| 1 | 실현손익 |
| 2 | 미실현손익 |
| 3 | 배당/이자 |
| 4 | 수수료 |
| 5 | 세금 |
| 6 | 순 투자성과 |

초기 구현은 리스트형 카드로 충분합니다. 이후 막대형 waterfall chart를 추가할 수 있습니다.

### 3. Cash Flow Separation

투자성과에서 제외한 현금흐름을 분리해 보여줍니다.

| 항목 | 설명 |
| --- | --- |
| 외부 입금 | 사용자가 새로 넣은 돈 |
| 외부 출금 | 사용자가 뺀 돈 |
| 매매 결제 | 매수/매도 때문에 움직인 현금 |
| 내부 이동 | 계좌 이체와 환전 |

이 카드는 "총자산은 늘었지만 투자로 번 것은 아님"을 설명하는 핵심 영역입니다.

### 4. Monthly Trend

월별 순 실현성과를 보여줍니다.

MVP에서는 최근 12개월 리스트를 사용하고, 제품화 단계에서 막대 차트로 확장합니다.

표시 항목:

- 월
- 순 실현성과
- 실현손익
- 배당/이자
- 수수료/세금

월별 미실현손익은 스냅샷 기준 기간 비교가 필요하므로 Phase 5에서 추가합니다.

### 5. Holding Contribution

종목별 성과 기여를 보여줍니다.

| 컬럼 | 내용 |
| --- | --- |
| 종목 | 이름, 심볼, 자산군 |
| 실현손익 | 매도 확정 손익 |
| 미실현손익 | 현재 보유 평가손익 |
| 배당/이자 | 해당 종목 수입 |
| 총 성과 | 실현 + 미실현 + 배당/이자 |
| 기여도 | 전체 순 투자성과 대비 비중 |

정렬 옵션:

- 총 성과 높은 순
- 총 성과 낮은 순
- 실현손익 높은 순
- 미실현손익 높은 순
- 배당/이자 높은 순

### 6. Drill-Down

항목을 탭하면 해당 성과를 만든 거래 이벤트 목록을 보여줍니다.

1차 범위:

- 종목 row 탭 -> 보유 상세 또는 종목 성과 상세
- 월 row 탭 -> 해당 월의 성과 관련 거래 목록
- 비용 row 탭 -> 수수료/세금 거래 목록

초기에는 기존 상세 화면으로 이동하고, 별도 상세 화면은 Phase 4에서 추가합니다.

## Data And API Changes

### Required Query Enhancements

기존 aggregate는 전체 기간 기준입니다. 기간 필터를 위해 아래 API를 추가합니다.

| API | 목적 |
| --- | --- |
| `fetchLedgerPortfolioPerformanceByCurrency({DateTime? from, DateTime? to})` | 기간별 전체 성과 |
| `fetchLedgerMonthlyPerformanceByCurrency({DateTime? from, DateTime? to})` | 기간별 월간 성과 |
| `fetchLedgerHoldingPerformanceByHoldingId({DateTime? from, DateTime? to})` | 기간별 종목 성과 |
| `fetchLedgerPerformanceEvents({from, to, action, holdingId})` | drill-down 거래 목록 |

기간 조건은 `transaction_events.occurred_at` 기준으로 적용합니다. 기존 데이터에 `YYYY.MM.DD` 형식이 섞일 수 있으므로 쿼리에서는 현재 코드처럼 `REPLACE(te.occurred_at, '.', '-')`를 사용해 비교 기준을 통일합니다.

### Date Range Model

UI와 DB 사이에 공통 기간 모델을 둡니다.

```dart
class PerformanceDateRange {
  const PerformanceDateRange({
    required this.label,
    this.from,
    this.to,
  });

  final String label;
  final DateTime? from;
  final DateTime? to;
}
```

직접 선택을 제외한 기본 preset:

| Preset | from | to |
| --- | --- | --- |
| 1개월 | 오늘 기준 1개월 전 | 오늘 |
| 3개월 | 오늘 기준 3개월 전 | 오늘 |
| 6개월 | 오늘 기준 6개월 전 | 오늘 |
| 올해 | 올해 1월 1일 | 오늘 |
| 전체 | null | null |

### Currency Conversion

현재 MVP처럼 통화별 ledger 집계를 먼저 만든 뒤 화면에서 KRW로 환산합니다.

단기 원칙:

- KRW는 그대로 사용합니다.
- USD는 `fetchLatestExchangeRate()`의 최신 환율로 환산합니다.
- 다른 통화가 추가되면 `ExchangeRates`를 통화 코드별로 조회하도록 확장합니다.

장기 원칙:

- 월별 과거 성과는 최신 환율이 아니라 거래 시점 또는 월말 환율을 쓰는 것이 더 정확합니다.
- 이 개선은 Phase 4로 분리합니다.

## Development Phases

### Phase 1. Calculation Contract Lock

목표: 화면보다 먼저 계산 정의와 테스트를 고정합니다.

작업:

- 성과 지표 정의를 `docs/data_and_sync.md` 또는 본 문서에 연결합니다.
- `LedgerPortfolioPerformanceRecord.pureRealizedPerformance` 정의를 테스트합니다.
- fee/tax가 성과에서 차감되는지 테스트합니다.
- deposit/withdrawal/transfer/fx가 순 투자성과에 섞이지 않는지 테스트합니다.
- 기존 `transaction_ledger_redesign.md`의 Phase 10 규칙과 용어를 맞춥니다.

완료 기준:

- 전체 포트폴리오 순 실현성과 테스트 통과
- 제외 현금흐름 테스트 통과
- 기존 `flutter test` 통과

### Phase 2. Date Range Support

목표: 전체 기간만 보던 리포트를 기간별로 탐색할 수 있게 합니다.

작업:

- `PerformanceDateRange` 모델을 추가합니다.
- portfolio, monthly, holding aggregate 쿼리에 `from/to` 조건을 추가합니다.
- 직접 선택 전에는 preset segmented control만 제공합니다.
- 화면 상태를 `StatefulWidget`으로 전환하고 선택 기간에 따라 reload합니다.

완료 기준:

- 전체, 올해, 1개월 등 preset 변경 시 모든 카드가 같은 기간 기준으로 갱신됩니다.
- 기간 필터 테스트가 거래 발생일 기준으로 통과합니다.

### Phase 3. Report UX Upgrade

목표: 현재 카드 나열형 화면을 리포트처럼 읽히게 만듭니다.

작업:

- 상단 summary header를 기간 선택 + 대표 지표 중심으로 재구성합니다.
- 성과 구성 카드를 순서 있는 breakdown 형태로 정리합니다.
- 제외 현금흐름 카드에서 입금/출금과 내부 이동을 더 명확히 분리합니다.
- 월별 성과는 최근 12개월 기본 노출로 제한하고 더보기 흐름을 준비합니다.
- 종목별 성과 row에 기여도와 정렬 옵션을 추가합니다.

완료 기준:

- 사용자가 순 투자성과, 순 실현성과, 제외 현금흐름을 구분할 수 있습니다.
- 모바일 폭에서 숫자와 라벨이 겹치지 않습니다.
- empty state가 거래 없음, 보유 없음, 기간 내 데이터 없음을 구분합니다.

### Phase 4. Drill-Down

목표: 집계 숫자의 근거 거래까지 내려갈 수 있게 합니다.

작업:

- `fetchLedgerPerformanceEvents()`를 추가합니다.
- 월별 row, 종목 row, 비용 row에서 관련 거래 목록을 열 수 있게 합니다.
- 1차 구현은 bottom sheet 또는 기존 상세 화면 이동 중 하나를 선택합니다.
- 거래 목록에는 날짜, 이벤트 종류, 종목/계좌, 금액, 성과 반영 항목을 표시합니다.

완료 기준:

- 특정 월의 순 실현성과를 만든 거래를 확인할 수 있습니다.
- 특정 종목의 실현손익/배당/이자 근거를 확인할 수 있습니다.

### Phase 5. Snapshot-Based Unrealized Trend

목표: 월별 리포트에 미실현손익 변화까지 포함합니다.

작업:

- 기간 시작/끝 snapshot을 조회합니다.
- 보유 종목별 평가손익 변화와 신규 매수/매도 영향을 분리할 수 있는지 검증합니다.
- 월말 snapshot이 없는 경우 가장 가까운 이전 snapshot을 사용할지 정책을 정합니다.
- 월별 순 투자성과에 실현성과와 평가손익 변화를 함께 표시합니다.

완료 기준:

- 월별 리포트에서 실현성과와 평가손익 변화가 분리됩니다.
- snapshot 누락 시 UI가 계산 한계를 명확히 보여줍니다.

### Phase 6. Historical FX Accuracy

목표: 외화 성과의 KRW 환산 정확도를 높입니다.

작업:

- 거래 시점 환율 또는 월말 환율 저장/조회 정책을 정합니다.
- `ExchangeRates`를 날짜와 통화 코드 기준으로 확장할지 검토합니다.
- 기존 최신 환율 환산과 과거 환율 환산의 차이를 테스트합니다.

완료 기준:

- 외화 실현손익, 배당, 수수료/세금이 기간 리포트에서 일관된 환율 정책으로 계산됩니다.

## Recommended MVP Scope

가장 먼저 개발할 범위는 Phase 1부터 Phase 3까지입니다.

포함:

- 기간 preset
- 전체 성과 요약
- 실현손익, 미실현손익, 배당/이자, 수수료, 세금 breakdown
- 제외 현금흐름 분리
- 월별 순 실현성과
- 종목별 총 성과와 기여도
- 계산 테스트

제외:

- 과거 환율 기반 KRW 환산
- 월별 미실현손익 변화
- 완전한 거래 drill-down 전용 화면
- 세후 예상 수익률

### Unit Tests

| 테스트 | 검증 내용 |
| --- | --- |
| pure realized performance | `realized + income - fee - tax` |
| excluded cash flow | deposit/withdrawal/transfer/fx가 순 성과에 포함되지 않음 |
| date range filter | 기간 밖 거래가 집계에서 제외됨 |
| monthly grouping | `YYYY.MM.DD`와 `YYYY-MM-DD` 날짜가 같은 월로 그룹됨 |
| currency merge | USD 금액이 지정 환율로 KRW 환산됨 |
| closed holding inclusion | 전량 매도 종목도 ledger activity가 있으면 성과에 포함됨 |

### Widget Tests

| 테스트 | 검증 내용 |
| --- | --- |
| empty state | 기간 내 거래가 없을 때 안내 표시 |
| preset switch | 기간 변경 시 표시 값 갱신 |
| breakdown card | 수수료/세금이 음수 성과로 표시 |
| holding ranking | 성과 정렬이 올바르게 적용 |

### Manual QA

1. 입금만 있는 계정에서 순 투자성과가 0인지 확인합니다.
2. 매수만 있고 가격 변화가 없는 계정에서 순 실현성과가 0인지 확인합니다.
3. 매도 손익이 있는 종목이 실현손익에 반영되는지 확인합니다.
4. 배당/이자 거래가 수입에 반영되는지 확인합니다.
5. 수수료/세금이 성과를 낮추는지 확인합니다.
6. 환전과 계좌 이체가 내부 이동으로만 표시되는지 확인합니다.
7. 전량 매도한 종목이 종목별 실현손익 랭킹에 남는지 확인합니다.

## Feasibility And Feedback

### Overall Assessment

이 계획은 MONEYFY의 현재 구조와 잘 맞습니다. 이미 정규화된 ledger table, 성과 aggregate API, 투자성과 화면, 스냅샷, 통화 환산 흐름이 있으므로 완전히 새로운 기능을 붙이는 것보다 구현 타당성이 높습니다.

가장 큰 장점은 앱의 포지션을 단순 자산 기록에서 성과 해석 도구로 끌어올린다는 점입니다. 사용자가 실제로 궁금해하는 것은 "총자산이 얼마인가"에서 끝나지 않고, "내가 잘해서 늘어난 돈인가, 그냥 입금해서 늘어난 돈인가"로 이어집니다. 이 리포트는 그 질문에 직접 답합니다.

다만 계획의 후반부에는 계산 정확도와 사용자 신뢰에 민감한 영역이 있습니다. 특히 기간별 미실현손익, 과거 환율, 대표 수익률은 단순 금액 집계보다 훨씬 해석 여지가 큽니다. 따라서 Phase 1-3은 강하게 추진하고, Phase 5-6은 별도 설계 검증 후 진행하는 것이 적절합니다.

### Feasibility Review

| 항목 | 타당성 | 판단 |
| --- | --- | --- |
| 원장 기반 전체 성과 집계 | 높음 | `transaction_lines` 기반 API가 이미 있어 확장 비용이 낮음 |
| 기간 필터 | 높음 | `transaction_events.occurred_at` 기준으로 쿼리 조건을 추가하면 됨 |
| 월별 순 실현성과 | 높음 | 현재 월별 aggregate가 이미 있고 테스트로 고정 가능 |
| 종목별 성과 기여도 | 중간-높음 | 종목별 ledger 성과는 가능하지만 수수료/세금 배부 정책이 필요함 |
| 제외 현금흐름 분리 | 높음 | deposit, withdrawal, transfer, fx action이 이미 분리되어 있음 |
| Drill-down 거래 목록 | 중간 | 데이터는 만들 수 있지만 UI 범위가 커질 수 있음 |
| 월별 미실현손익 변화 | 중간-낮음 | snapshot 의존도가 높고 누락/가격 갱신 상태에 따라 해석이 흔들림 |
| 과거 환율 기반 환산 | 중간-낮음 | 정확도는 좋아지지만 환율 데이터 모델 확장이 필요함 |
| 대표 수익률 | 낮음-중간 | 단순 수익률은 쉽지만 입출금 timing 반영 수익률은 설계 난도가 높음 |

### Expected Effects

#### Product Effects

- 사용자가 총자산 변화와 투자성과를 분리해서 이해할 수 있습니다.
- 입금 때문에 자산이 늘어난 경우와 투자 수익으로 늘어난 경우를 구분할 수 있습니다.
- 분석 탭의 존재 이유가 더 명확해집니다.
- 배당/이자, 수수료/세금, 실현손익이 한 화면에 모이므로 반복 방문 가치가 생깁니다.
- 이후 리밸런싱, 월간 리포트, AI 진단의 입력 데이터로 재사용할 수 있습니다.

#### Technical Effects

- ledger model을 실제 사용자 가치로 연결합니다.
- legacy transaction text parsing 의존도를 더 줄일 수 있습니다.
- 성과 계산 규칙을 테스트로 고정해 이후 기능 확장 시 회귀를 줄입니다.
- 기간 필터와 drill-down API는 다른 분석 화면에서도 재사용 가능합니다.
- 스냅샷 기반 분석과 ledger 기반 분석의 역할을 더 명확히 나눌 수 있습니다.

#### UX Effects

- 사용자는 "돈이 얼마나 늘었는지"보다 "왜 늘었는지"를 읽을 수 있습니다.
- 비용과 세금이 숨지 않고 보이기 때문에 성과 체감이 더 현실적입니다.
- 종목별 기여도가 추가되면 포트폴리오 점검 행동으로 자연스럽게 이어집니다.
- 기간 preset이 들어가면 분석 화면이 정적인 요약이 아니라 탐색 도구가 됩니다.

### Strengths

1. 기존 구조와 궁합이 좋습니다.

   `TransactionEvents`, `TransactionLines`, `LedgerPortfolioPerformanceRecord`, `InvestmentPerformancePage`가 이미 존재하므로 새 schema를 크게 만들 필요가 없습니다.

2. 사용자 체감 가치가 큽니다.

   총자산 앱에서 흔히 생기는 착시인 "입금해서 늘어난 자산"과 "투자로 번 돈"을 분리합니다.

3. 계산 규칙을 제품 언어로 만들 수 있습니다.

   실현손익, 미실현손익, 배당/이자, 수수료/세금, 제외 현금흐름을 일관된 용어로 묶을 수 있습니다.

4. 후속 기능의 기반이 됩니다.

   리밸런싱 제안, 월간 리포트, 종목별 뉴스 영향도, AI 진단이 이 성과 분해 결과를 사용할 수 있습니다.

5. MVP와 고급 기능을 분리하기 쉽습니다.

   Phase 1-3만으로도 가치가 있고, Phase 5-6은 정확도 요구가 높으므로 나중에 진행할 수 있습니다.

### Weaknesses And Trade-Offs

1. 사용자가 용어를 어렵게 느낄 수 있습니다.

   순 실현성과, 순 투자성과, 결제 현금흐름, 내부 이동 같은 용어는 정확하지만 처음 보는 사용자에게는 부담이 될 수 있습니다. UI에서는 문서식 용어를 그대로 많이 노출하기보다 짧은 라벨과 보조 설명을 함께 써야 합니다.

2. 기간별 미실현손익은 정확도 리스크가 큽니다.

   특정 기간의 평가손익 변화를 정확히 보려면 시작점과 끝점의 가격, 수량, 원가, 환율이 모두 일관되어야 합니다. snapshot이 없거나 가격 갱신이 늦으면 사용자가 숫자를 신뢰하기 어렵습니다.

3. 최신 환율 환산은 과거 성과를 왜곡할 수 있습니다.

   MVP에서는 최신 환율을 쓰는 것이 단순하지만, 과거 USD 배당이나 매도 손익을 현재 환율로 환산하면 실제 당시 원화 가치와 다를 수 있습니다.

4. 수수료/세금 배부 정책이 애매합니다.

   거래에 붙은 수수료/세금은 종목에 배부할 수 있지만, standalone fee/tax는 포트폴리오 비용으로 남겨야 할 수 있습니다. 종목별 총 성과에 비용을 어디까지 반영할지 명확히 정해야 합니다.

5. 수익률을 너무 빨리 넣으면 오해를 만들 수 있습니다.

   단순 수익률은 구현하기 쉽지만 입출금 timing이 많은 사용자에게는 부정확합니다. 시간가중수익률이나 금액가중수익률은 더 정확하지만 구현과 설명이 어렵습니다.

### Opportunities

- 월간 리포트 자동 생성 기능의 핵심 데이터가 됩니다.
- AI 포트폴리오 진단이 단순 비중 평가를 넘어서 "성과 원인"까지 설명할 수 있습니다.
- 종목 뉴스 요약과 결합하면 "성과가 큰 종목의 최근 이슈"를 우선 보여줄 수 있습니다.
- 사용자가 잘못 입력한 거래를 찾는 reconciliation UX로 확장할 수 있습니다.
- 향후 export 기능에서 성과 리포트 PDF/CSV를 만들 수 있습니다.

### Threats

- 계산 결과가 대시보드, 스냅샷, 보유 상세와 다르게 보이면 신뢰가 떨어집니다.
- 일부 거래 유형이 ledger line으로 제대로 변환되지 않으면 특정 사용자의 성과가 틀어질 수 있습니다.
- 외화 자산이 많은 사용자에게 최신 환율 환산은 큰 차이를 만들 수 있습니다.
- drill-down 없이 집계 숫자만 보여주면 숫자의 근거를 확인하기 어렵습니다.
- 분석 화면이 카드와 숫자로 과밀해지면 핵심 메시지가 흐려질 수 있습니다.

### Recommended Adjustments

1. Phase 1-3을 첫 릴리스 범위로 유지합니다.

   이 범위는 구현 타당성과 사용자 가치의 균형이 가장 좋습니다. 기간 필터, 성과 breakdown, 제외 현금흐름, 종목별 기여도까지가 첫 제품화에 적합합니다.

2. 수익률은 첫 릴리스에서 제외하거나 실험 배지로 둡니다.

   금액 중심 리포트를 먼저 안정화하고, 수익률은 별도 문서에서 단순 수익률, 시간가중수익률, 금액가중수익률을 비교한 뒤 결정하는 편이 안전합니다.

3. 월별 미실현손익은 snapshot 품질 점검 후 진행합니다.

   월말 snapshot 누락, 가격 갱신 실패, 환율 누락이 있을 때의 fallback 정책을 먼저 정해야 합니다.

4. 외화 리포트에는 환산 기준을 반드시 표시합니다.

   MVP에서 최신 환율을 쓴다면 "최신 환율 기준 원화 환산"처럼 짧게 표시해 해석 리스크를 줄입니다.

5. 종목별 비용 배부는 단계적으로 갑니다.

   1차는 종목별 성과를 `실현손익 + 미실현손익 + 배당/이자`로 보여주고, 수수료/세금은 포트폴리오 비용에 둡니다. 이후 거래에 명확히 연결된 비용만 종목에 배부하는 정책을 추가합니다.

6. Drill-down은 늦추지 않는 편이 좋습니다.

   집계 숫자의 신뢰는 근거 확인에서 나옵니다. 완전한 상세 화면이 아니어도, bottom sheet로 해당 숫자를 만든 거래 목록을 보여주는 최소 기능은 Phase 4에서 우선순위를 높게 둡니다.

### Final Recommendation

이 계획은 진행할 만합니다. 특히 Phase 1-3은 기술적으로도 현실적이고, 사용자 가치도 분명합니다. 다만 정확도가 민감한 기능을 한 번에 모두 넣기보다, 다음 순서로 잘라 가는 것이 좋습니다.

1. 금액 기준 성과 리포트 안정화
2. 기간 필터와 종목별 기여도 추가
3. 집계 근거 drill-down 추가
4. snapshot 기반 미실현손익 추세 검증
5. 과거 환율과 수익률 정책 설계

첫 릴리스의 핵심 문장은 다음과 같이 잡는 것이 좋습니다.

```text
입출금과 내부 이동을 제외하고, 투자로 만든 성과만 분리해서 보여준다.
```

이 문장에 맞지 않는 기능은 첫 릴리스에서 제외하면 범위가 건강하게 유지됩니다.
