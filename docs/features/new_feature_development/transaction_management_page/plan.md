# Transaction Management Page Plan

## Product Goal

사용자가 자산 상세 화면이나 현금 계좌 상세 화면에 들어가지 않아도 전체 거래 내역을 한 곳에서 보고 직접 추가, 수정, 삭제할 수 있는 거래 관리 화면을 제공한다. 거래가 많아진 뒤에도 빠르게 찾을 수 있도록 검색, 필터, 정렬 조회 기능을 제공한다.
과거 거래를 단순 기록으로 보강할 수 있도록 기본값은 포트폴리오 계산 미반영으로 두고, 사용자가 명시적으로 켠 거래만 보유/현금/성과 계산에 반영한다.

## Current Baseline

- 거래 내역은 보유 종목 상세와 현금 계좌 상세의 섹션으로만 노출된다.
- 투자 거래는 `TransactionFormPage`, 현금 거래는 `CashTransactionFormPage`에서 생성/수정된다.
- 삭제는 상세 화면의 거래 행에서 `AppDatabase.deleteLedgerTransactionItem`과 `SyncService.syncNow`를 통해 처리된다.
- 전체 거래 목록 전용 탭이나 페이지는 없다.
- 거래 탭 초기 구현은 전체 목록과 CRUD에 집중했고, 검색/필터/정렬 조회는 아직 없다.
- 기존 거래 저장 폼은 저장 즉시 보유 수량, 현금 잔액, 성과 원장에 반영된다.

## Success Criteria

- 하단 내비게이션에서 거래 전용 화면에 진입할 수 있다.
- 모든 보유 종목과 현금 계좌의 거래 내역이 날짜 최신순으로 표시된다.
- 사용자는 거래 화면에서 거래를 추가, 수정, 삭제할 수 있다.
- 사용자는 거래명, 계좌명, 자산명, 날짜, 유형으로 거래를 검색할 수 있다.
- 사용자는 전체/투자/현금/입금·수익/출금·매수 기준으로 목록을 필터링할 수 있다.
- 사용자는 최신순, 오래된순, 금액 큰순, 금액 작은순으로 목록을 정렬할 수 있다.
- 거래 추가/수정 시 `포트폴리오 계산에 반영` 토글을 제공하고 기본값은 꺼짐이다.
- 계산 미반영 거래는 거래 목록에는 보이지만 보유 수량, 평단, 현금 잔액, 성과 집계에는 영향을 주지 않는다.
- 투자 거래와 현금 거래는 기존 폼과 DB API를 재사용해 원장 정합성을 유지한다.
- 데이터 교체, 로그아웃 정리, 원격 새로고침 흐름이 기존 탭과 같은 규칙을 따른다.

## Metric And Data Definitions

- 표시 대상은 `AppDatabase.fetchAssets()`가 반환하는 활성 자산의 활성 보유/현금 계좌 거래다.
- 기본 거래 정렬은 `TransactionItem.date` 기준 내림차순, 같은 날짜는 로드된 원장 순서의 역순으로 한다.
- 금액 정렬은 거래 탭에 표시하는 KRW 환산 금액 기준으로 한다.
- 계산 미반영 거래는 `transaction_events.source = 'record_only'`로 저장하고, 계산 쿼리에서는 제외한다.
- 계산 미반영 거래도 표시용 `transaction_lines`를 남겨 거래 목록, 검색, 수정, 삭제가 가능하게 한다.
- 투자 거래 금액은 보유 종목의 통화/환율로 표시한다.
- 현금 거래 금액은 현금 계좌의 통화/환율로 표시한다.
- 삭제는 원장 이벤트와 연결된 legacy mirror를 함께 soft delete하는 기존 DB API를 사용한다.

## Proposed UX

- 하단 탭에 `거래`를 추가한다.
- 화면 상단 액션 버튼으로 거래를 추가한다.
- 추가 시 계좌 선택 바텀시트를 띄워 투자 보유 종목 또는 현금 계좌를 선택하고, 선택한 대상에 맞는 기존 거래 폼을 연다.
- 거래 행을 탭하면 수정 폼을 연다.
- 거래 행은 기존 상세 화면처럼 스와이프 삭제를 지원한다.
- 거래가 없으면 빈 상태와 거래 추가 액션을 보여준다.
- 목록 상단에 검색 입력, 필터 chip, 정렬 메뉴를 배치한다.
- 검색/필터 결과가 없으면 조건 초기화 액션을 제공한다.
- 거래 폼에는 계산 반영 여부 토글을 배치한다. 기본은 꺼짐이며, 켜면 기존과 같은 실제 거래로 저장한다.

## Data And API Changes

- DB schema 변경은 없다.
- 신규 page-level view model은 `fetchAssets()` 결과를 평탄화해서 사용한다.
- 기존 생성/수정/삭제 API를 재사용한다.
- `createTransaction`과 `updateTransactionItem`은 계산 반영 여부를 인자로 받아 `ledger` 또는 `record_only` 원장 이벤트를 생성한다.
- 계산/성과/상태 parity 쿼리는 `record_only` source를 제외한다.
- 별도 sync endpoint 변경은 없다.

## Development Phases

1. 거래 관리 페이지 추가 및 전체 거래 평탄화 모델 구현.
2. 계좌 선택 바텀시트와 기존 거래 폼 연결.
3. 거래 행 수정/삭제, 새로고침, 빈/오류/로딩 상태 구현.
4. 앱 셸 하단 탭 연결과 데이터 교체 scope 반영.
5. walkthrough 및 거래 흐름 테스트 보강.
6. 검색, 필터, 정렬 조회 state와 UI 추가.
7. 계산 반영 토글과 record-only 원장 저장 정책 추가.

## MVP Scope

- 전체 거래 목록, 추가, 수정, 삭제.
- 기존 투자/현금 거래 폼 재사용.
- 날짜 최신순 정렬.
- 검색, 필터, 정렬 조회.
- 기본 계산 미반영 거래 추가/수정.
- pull-to-refresh와 원격 sync 후 local reload.

## Out Of Scope

- 기간 선택, CSV export.
- 거래 bulk edit.
- 원장 라인 단위 고급 분해/병합 UI.
- 새로운 DB schema 또는 Supabase migration.

- `flutter test test/page_walkthrough_test.dart`
- `flutter test test/transaction_flow_test.dart`
- `flutter analyze`
- 수동 QA: 거래 탭 진입, 추가 계좌 선택, 투자/현금 거래 수정, 삭제 확인.
- 수동 QA: 검색어, 필터, 정렬 조합별 결과 확인.
- 수동 QA: 계산 미반영 거래 추가 후 보유 수량/현금 잔액이 변하지 않는지 확인.

## Risks And Decisions

- 이체/환전처럼 한 이벤트가 여러 라인을 만드는 거래는 행이 둘 이상 표시될 수 있다. MVP에서는 기존 현금 상세 화면과 같은 표시 정책을 유지한다.
- 직접 수정할 수 없는 원장 라인은 기존 상세 화면과 같은 안내 문구를 보여주고 수정 폼 진입을 막는다.
- 하단 탭이 6개가 되어 좁은 화면에서 혼잡할 수 있다. MVP에서는 짧은 `거래` 라벨과 아이콘으로 유지하고, 후속 UX에서 탭 재배치를 검토한다.
- 기본값을 계산 미반영으로 바꾸면 사용자가 실제 거래 반영을 놓칠 수 있다. 토글 라벨과 설명을 명확히 표시한다.

## Open Questions

- 이체/환전을 하나의 대표 행으로 묶어 보여줄지.
- 거래 화면을 탭 대신 포트폴리오 또는 My의 하위 페이지로 옮길지.

## Feasibility And Feedback

- 기존 `fetchAssets()`, `TransactionFormPage`, `CashTransactionFormPage`, `deleteLedgerTransactionItem`을 재사용할 수 있어 schema 변경 없이 구현 가능하다.
- 사용자 체감 효과는 높다. 자산별 상세 화면을 찾아 들어가는 단계를 줄인다.
- 데이터 정확도 리스크는 낮지만, 원장 기반 투자 거래와 현금 거래의 편집 가능 조건을 상세 화면과 동일하게 유지해야 한다.
- UI 복잡도는 계좌 선택 바텀시트와 전체 거래 행에 집중된다. 검색/필터는 MVP에서 제외해 범위를 고정한다.
- 첫 개발 batch는 페이지, 평탄화 모델, 앱 셸 탭 연결이다. 두 번째 batch는 CRUD 액션과 테스트다.
