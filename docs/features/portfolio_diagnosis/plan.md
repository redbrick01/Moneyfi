# Portfolio Diagnosis Redesign Plan

이 문서는 MONEYFY의 `포트폴리오 MVP 분석` 화면을 제품급 `포트폴리오 진단` 경험으로 재설계하기 위한 계획서입니다.

## Product Goal

사용자가 포트폴리오 분석 화면에 들어왔을 때 많은 지표를 해석하는 대신, 현재 상태와 우선 확인해야 할 문제, 조정 후보를 빠르게 이해하도록 돕습니다.

핵심 질문은 다음 네 가지입니다.

1. 내 포트폴리오는 지금 괜찮은가?
2. 무엇이 문제인가?
3. 어디를 조정해야 하는가?
4. 근거 데이터를 더 보고 싶다면 어디서 확인하는가?

## Current Baseline

현재 구현은 `lib/pages/portfolio_analysis_mvp_page.dart`에 있으며 분석 탭의 `포트폴리오 MVP 분석` 카드에서 진입합니다.

| 영역 | 현재 상태 |
| --- | --- |
| 진입점 | `lib/pages/analysis_page.dart`의 `포트폴리오 MVP 분석` 카드 |
| 화면 | `PortfolioAnalysisMvpPage` |
| 데이터 | 자산, 목표 비중, 최근 60개 스냅샷 |
| 주요 섹션 | 분석 요약, 목표 비중 리밸런싱, 성과 기여도, 자산 변화 원인, MDD, 집중도 위험 |
| 구조 문제 | 모든 분석이 같은 계층으로 나열되어 사용자의 판단 순서가 약함 |
| 표현 문제 | 설명 문구가 기능 설명 중심이고 행동 판단을 돕는 문장이 부족함 |

기존 화면은 계산과 실험 기능을 빠르게 모아둔 MVP에 가깝습니다. 이번 리디자인은 기존 레이아웃을 유지하지 않고, 정보 구조와 사용자 흐름을 새로 정의합니다.

## Success Criteria

| 기준 | 목표 |
| --- | --- |
| 이해 가능성 | 첫 화면에서 전체 상태와 핵심 경고를 5초 안에 파악할 수 있음 |
| 의사결정성 | 위험 신호와 조정 후보가 기존 상세 지표보다 먼저 노출됨 |
| 정보 구조 | 요약, 위험, 조정, 성과 원인, 상세 분석이 명확히 분리됨 |
| 문구 품질 | 기능 설명보다 사용자 해석 중심의 문장을 사용함 |
| 확장성 | 추후 AI 요약, 기간 선택, 리밸런싱 시뮬레이션을 붙일 수 있는 구조 |
| 검증 가능성 | 화면 진입과 주요 문구가 widget test로 고정됨 |

## Metric And Data Definitions

이번 1차 리디자인은 새 DB schema나 원격 API를 추가하지 않습니다. 기존 화면의 데이터 계약을 유지합니다.

| 지표 | 정의 | 데이터 기준 |
| --- | --- | --- |
| 총자산 | 표시 대상 자산의 평가금액 합계 | `AssetItem.totalValuationAmount` |
| 평가손익 | 총자산 - 총매입금액 | `AssetItem.totalValuationAmount - totalPurchaseAmount` |
| 수익률 | 평가손익 / 총매입금액 | 총매입금액이 0 이하이면 0 |
| 목표 이탈 | 현재 비중 - 목표 비중 | 목표 비중이 설정된 자산만 계산 |
| 조정 후보 금액 | 목표 이탈률 * 총자산 | 양수는 축소 후보, 음수는 확대 후보 |
| 최대 낙폭 | 최근 스냅샷 고점 대비 최저 하락률 | 최근 60개 스냅샷 기준 |
| 집중도 HHI | 자산 비중 제곱 합 * 10000 | 표시 대상 자산 기준 |
| 상위 3개 비중 | 자산 비중 상위 3개의 합 | 표시 대상 자산 기준 |

## Proposed UX

### 1. Diagnosis Header

상단은 한 문장 진단과 핵심 수치 4개를 보여줍니다.

| 요소 | 내용 |
| --- | --- |
| 화면 이름 | `포트폴리오 진단` |
| 보조 문구 | `위험 신호와 조정 후보를 먼저 확인해요` |
| 상태 배지 | `양호`, `주의`, `위험`, `데이터 부족` |
| 대표 문장 | 가장 중요한 경고 또는 긍정 상태 1개 |
| 핵심 수치 | 총자산, 수익률, 목표 이탈, 최대 낙폭 |

예시 문구:

```text
상위 자산 비중이 높아 변동성에 취약할 수 있어요.
```

### 2. Attention Items

`주의가 필요한 항목` 섹션은 사용자가 먼저 확인해야 할 위험 신호를 리스트로 보여줍니다.

포함 항목:

| 항목 | 표시 조건 |
| --- | --- |
| 집중도 | 상위 1개 또는 상위 3개 비중, HHI 기준 |
| 낙폭 | 최근 60개 스냅샷 기준 MDD |
| 목표 비중 이탈 | 목표가 설정된 자산의 최대 이탈률 |
| 성과 악화 | 손실 금액이 큰 자산 |

각 행은 제목, 짧은 해석 문장, 수치 배지로 구성합니다.

### 3. Adjustment Suggestions

리밸런싱은 `조정 제안`으로 이름을 바꾸고 행동 판단에 맞게 재구성합니다.

구성:

| 상태 | 의미 |
| --- | --- |
| 축소 후보 | 목표보다 많이 보유한 자산 |
| 확대 후보 | 목표보다 적게 보유한 자산 |
| 정상 범위 | 목표와 큰 차이가 없는 자산 |

투자 조언으로 오해되지 않도록 `매도`, `매수` 대신 `축소 후보`, `확대 후보`, `점검` 표현을 사용합니다.

### 4. Performance Story

`성과 기여도`와 `자산 변화 원인`은 `무엇이 자산을 움직였나요?`로 묶습니다.

상단에는 총자산 변화, 평가손익 변화, 입출금/원금 변화 추정을 보여주고, 하단에는 성과 기여도가 큰 자산을 리스트로 표시합니다.

### 5. Detailed Analysis

MDD와 HHI 설명은 상세 영역으로 이동합니다. 첫 화면에서는 상태와 해석을 먼저 보여주고, 계산식이나 기관 기준 설명은 상세 섹션에서 확인하도록 합니다.

## Data And API Changes

1차 리디자인에서는 DB, Supabase Edge Function, sync 로직을 변경하지 않습니다.

필요한 화면 내부 모델:

| 모델 | 목적 |
| --- | --- |
| `_DiagnosisSummary` | 전체 상태, 대표 문장, 핵심 지표 |
| `_AttentionItem` | 위험 신호 리스트 |
| `_AdjustmentSuggestion` | 목표 대비 조정 후보 |

기존 `_PortfolioAnalysisMvpData`에서 파생 계산을 수행합니다.

## Development Phases

### Phase 1. Documentation And Contract

- 본 계획서를 작성합니다.
- 검증 계획과 임시 실행 계획을 분리합니다.
- 기존 데이터 정의를 명시합니다.

완료 기준:

- `docs/features/portfolio_diagnosis/plan.md`가 존재합니다.
- `docs/README.md`에 영구 문서 링크가 추가됩니다.

### Phase 2. IA And Entry Rename

- 분석 탭 진입 카드명을 `포트폴리오 진단`으로 변경합니다.
- 화면 제목과 보조 문구를 사용자 가치 중심으로 변경합니다.
- 기존 `MVP`, `테스트 화면` 문구를 제거합니다.

완료 기준:

- 사용자가 개발 단계 명칭을 보지 않습니다.
- 기존 화면 진입 테스트가 새 문구 기준으로 통과합니다.

### Phase 3. Diagnosis Header And Attention Items

- 상단 진단 요약을 추가합니다.
- 위험 신호 리스트를 추가합니다.
- 총자산, 수익률, 목표 이탈, 최대 낙폭을 핵심 지표로 재배치합니다.

완료 기준:

- 첫 화면에서 상태, 경고, 핵심 수치가 먼저 보입니다.
- 상세 지표보다 위험 신호가 먼저 노출됩니다.

### Phase 4. Adjustment Suggestions

- 리밸런싱 섹션을 조정 제안으로 재구성합니다.
- 목표 비중이 없는 경우 해당 섹션에서만 안내합니다.
- 자산별 현재/목표/차이/금액을 한 행에 표시합니다.

완료 기준:

- 사용자가 축소 후보와 확대 후보를 구분할 수 있습니다.
- 투자 지시처럼 보이는 표현을 사용하지 않습니다.

### Phase 5. Performance Story And Details

- 성과 기여도와 자산 변화 원인을 하나의 해석 흐름으로 묶습니다.
- MDD와 HHI는 상세 분석 영역에서 확인하도록 낮은 계층으로 이동합니다.

완료 기준:

- 사용자 판단 흐름이 `상태 -> 위험 -> 조정 -> 근거` 순서로 읽힙니다.

이번 개발 배치에 포함합니다.

- 문서화
- 분석 탭 진입 카드명 변경
- 페이지 제목 변경
- 진단 요약 섹션 추가
- 주의 항목 섹션 추가

- 기존 성과/MDD/집중도 계산 재사용
- 관련 walkthrough test 갱신

이번 배치에서 제외합니다.

- DB schema 변경
- 원격 API 변경
- 실제 매수/매도 주문 연결
- AI 기반 자연어 진단 생성
- 기간 선택 UI
- 리밸런싱 시뮬레이션

자동 테스트:

```bash
flutter analyze
flutter test test/page_walkthrough_test.dart
flutter test test/ui_component_smoke_test.dart
```

필요 시 전체 회귀 테스트:

```bash
flutter test
```

수동 QA:

- 자산이 없을 때 빈 상태가 과도하게 넓지 않은지 확인합니다.
- 목표 비중이 없을 때 조정 제안 섹션만 안내 상태인지 확인합니다.
- 스냅샷이 부족해도 진단 요약과 조정 제안이 깨지지 않는지 확인합니다.
- 긴 자산명과 큰 금액이 모바일 폭에서 겹치지 않는지 확인합니다.
- 다크 모드에서 상태 배지와 경고 색상이 과도하게 강하지 않은지 확인합니다.

## Risks And Decisions

| 항목 | 결정 |
| --- | --- |
| 투자 조언 오해 | `매수/매도` 대신 `확대 후보/축소 후보`를 사용 |
| 데이터 정확도 | 기존 스냅샷과 자산 집계 계산을 재사용하고 새 계산은 파생값으로 제한 |
| UI 복잡도 | 차트보다 리스트와 요약 지표 중심으로 1차 구현 |
| 용어 난이도 | HHI, MDD는 상세 분석에서 보조 설명으로 노출 |
| 테스트 범위 | 화면 진입과 주요 문구는 widget test로 고정, 시각 QA는 수동 항목으로 남김 |

## Open Questions

- 목표 비중 이탈의 `정상 범위` 기준을 몇 %p로 둘지 정해야 합니다. 1차 구현은 3%p 이하를 정상 범위로 봅니다.
- 최대 낙폭의 위험 구간 기준은 기존 5%, 15%, 30%를 유지합니다.
- 향후 AI 진단 문장을 붙일 때 로컬 규칙 기반 문장과 어떻게 우선순위를 둘지 정해야 합니다.

## Feasibility And Feedback

### Fit With Existing Structure

기존 화면은 필요한 데이터 대부분을 이미 로드하고 있습니다. 따라서 1차 리디자인은 DB 변경 없이 화면 내부 정보 구조와 컴포넌트 재배치로 구현할 수 있습니다.

### Implementation Difficulty

난이도는 중간입니다. 계산 로직보다 UI 구조 변경이 중심이지만, 기존 파일이 길고 섹션 클래스가 많아 변경 범위를 조심스럽게 관리해야 합니다.

### User Impact

사용자 체감 효과는 큽니다. 기존 화면은 지표를 모두 읽어야 의미가 보였지만, 새 화면은 위험 신호와 조정 후보를 먼저 보여줍니다.

### Data Accuracy Risk

낮음입니다. 새 지표는 기존 값의 파생 계산이며 DB query를 바꾸지 않습니다. 다만 스냅샷 기간과 현재 자산 기준이 섞이는 영역은 문구로 기준을 명확히 해야 합니다.

### UI Complexity Risk

중간입니다. 진단 요약, 주의 항목, 조정 제안이 추가되면 화면이 다시 길어질 수 있습니다. 따라서 상세 계산 설명은 하단으로 내리고, 각 섹션의 문장을 짧게 유지합니다.

### Testability

자동 테스트는 화면 진입과 주요 문구 검증에 적합합니다. 반응형 겹침, 시각적 계층, 다크 모드는 수동 QA가 필요합니다.

### MVP Exclusions

이번 첫 개발 batch에는 기간 선택, AI 진단, 차트 고도화, 리밸런싱 시뮬레이션을 넣지 않습니다. 이들은 데이터 기준과 법적 표현 검토가 더 필요합니다.

### First Development Batch

첫 배치는 다음으로 확정합니다.

1. 문서와 검증 계획 작성
2. 분석 탭과 페이지 명칭 변경
3. 진단 요약과 주의 항목 추가
4. 리밸런싱을 조정 제안으로 재구성
5. 관련 테스트 갱신 및 검증
